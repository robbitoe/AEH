# ADR 0001: Runner hardening for MVP-1

Status: Accepted (owner approval, 2026-11-12)

## Context

A QA and security review of the MVP-1 runner found that the verified candidate could differ from the integrated commit, that level 2 could be accepted without review, that a quoted `VERDICT: APPROVE` could count as approval, that timeouts fell through to the gates, and that resume reused completed tasks without checking the contract. Fixing these changes decisions that need the owner's approval: the gate order, the ladder and how agent failures are handled.

## Decision

1. **Candidate commit.** After the agent finishes, AEH freezes the worktree as one commit on the pinned base. The hash and scope gates compare that commit with its base as Git objects in the main repository, so nothing from the candidate is checked out before they pass; the hash gate checks that the acceptance paths are identical to the base, which holds the sealed tests. Build, test and review then run on a clean, detached verification worktree of that commit. The integration branch advances to that exact SHA with a compare-and-swap (`git update-ref <ref> <new> <old>`). If the agent moved `HEAD`, the attempt fails before the hash gate and is reported as `scope`. Build, test or review that change the verification checkout, or set index flags that hide changes (`skip-worktree`, `assume-unchanged`), fail their gate.
2. **Agent failures.** A non-zero exit from the agent CLI fails the attempt without running the gates. The ladder continues as before: retry with feedback, then the next profile, then block.
3. **Timeouts and interruptions.** A timeout or cancellation of the agent, a gate or the reviewer kills its process tree, blocks the outcome immediately, without retry, and retains the affected worktree. The tree is killed only on timeout or cancellation: background processes left by a command that exits normally keep running. Both launch paths share a platform-specific runner and configure `exec.Cmd.Cancel`. Windows starts the child suspended, assigns it to a Job Object and then resumes every thread owned by its PID, including the primary thread; injected libraries may have created additional threads. Cancellation captures member process handles before terminating the job, captures additional members after termination, and waits for their process objects to become signaled within the existing two-second deadline. An empty active-process count alone does not prove handle teardown. A failed wait returns a cleanup error; external services such as file scanners may still briefly hold log files after process termination. Assignment and resume are synchronized with cancellation. This avoids a spawn-before-assignment race and tracks descendants even after intermediate MSYS launchers exit. It also avoids `taskkill`'s query permissions, which restricted Windows environments may deny. The implementation uses only standard-library Windows APIs. Unix starts a dedicated process group (`Setpgid`) and sends `SIGKILL` to that group. The signal context handles both interrupt and `SIGTERM`. `WaitDelay` remains a backstop. This is cleanup rather than isolation: Unix descendants that leave the group can escape. Windows processes started on the agent's behalf by another service can also escape the job, including WMI `Win32_Process.Create`, `schtasks`, out-of-process COM and `ShellExecute` via Explorer. Confirm the processes have stopped and inspect possible effects before answering.
4. **Level 2 review.** Level 2 requires a reviewer profile separate from the task's implementation profiles. A verdict counts only when the reviewer exits successfully and writes `VERDICT: APPROVE` or `VERDICT: REJECT` as the final nonempty line of plain stdout.
5. **Execution contract.** State records a SHA-256 of the outcome, sealed tests, prompts, build and test commands, `pass_env`, protected paths and limits, plus the verified branch head. Resume refuses when either differs. Profiles, task start profiles, ladder, reviewer, notify and timeouts are excluded, so a blocked outcome can resume after fixing a CLI flag or raising a timeout.
6. **Environment.** Agents, gate commands and the harness's own git calls inherit only OS and tool-discovery variables plus the names listed in `pass_env`. Credentials reach an agent only through `pass_env` or the profile's `env`. Harness git calls run with `--no-replace-objects`, `core.fsmonitor=false` and hooks disabled, because replace refs could swap the object behind a verified SHA and hooks or fsmonitor would run agent-written programs. Clean and smudge filters defined in Git config still run (see 9); an agent that can edit that config already runs with the user's permissions. This reduces accidental exposure; it is not isolation, since processes still run with the user's permissions.
7. **Diff limit.** Changes Git cannot count in lines (binaries) fail the scope gate.
8. **Agent instruction files.** `AGENTS.md`, `CLAUDE.md`, `CLAUDE.local.md`, `.claude/` and `.codex/` fail the scope gate in any directory, so a candidate cannot plant instructions that steer the reviewer. Path matching is case-insensitive on Windows and macOS.
9. **Git control files.** `.gitattributes`, `.gitmodules` and `.lfsconfig` fail the scope gate in any directory, and so does any change to a submodule pointer (gitlink), because the gates cannot see the submodule's content and a submodule commit could bring its own attributes. Harness diffs use `--ignore-submodules=none`, so `ignore` settings in `.gitmodules` or Git config cannot hide a pointer change. When `core.attributesFile` points inside the repository, that file is protected as well, since it selects filters the same way. A candidate therefore cannot select filters for anything AEH verifies: the verification checkout applies only the base's attributes, which the owner already trusts. One gap is accepted: while the harness captures the candidate (`git add -A` in the agent's worktree, before scope), the candidate's own attributes can select a clean filter the owner already configured, and that filter can run a script the candidate edited. The change then fails scope and build and test never run, so integrity holds; and the agent can already run any command with the user's permissions during its turn. Closing it needs Git 2.43 or later (`--attr-source=<base>` during capture) and is deferred to the process sandbox work.

## Consequences

- Accepted work is exactly the commit that passed the gates.
- Recovery after a crash is manual: remove the outcome lock and any retained worktrees and attempt branches.
- Outcomes cannot change `.gitattributes`, `.gitmodules`, `.lfsconfig` or submodule pointers; the owner changes them by hand.
- Outcomes cannot change binary files until a measurable limit for them is defined.
- A build or test command that leaves a background process holding its output (for example a Gradle or MSBuild daemon) ends with `exec.ErrWaitDelay`, so the gate counts as interrupted and the outcome blocks. Disable such daemons in `commands` until AEH handles it.
- Process isolation remains pending (sandbox without network, only the worktree mounted).
